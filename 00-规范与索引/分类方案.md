# work_doc 资料仓库分类方案

> 面向对象：仓库维护者（自己）+ 需要按问题检索资料的使用者
> 分析范围：`E:/基础学习/git相关/work_doc` 全量文件（106 个已跟踪文件 + 本地未跟踪的 docx 草稿与二进制包）
> 结论摘要：现有结构按「文件格式」分区，建议改为按「功能域」分区，格式降级为扩展名，板卡型号降级为元数据标签。

### 1.3 格式重复关系（关键）

- **同名同主题、md + pdf 双份**：12 篇（如 `python摄像头例程问题`、`板卡安装docker-ce`、`鲁班猫5安装zerotier`）
- **只有 docx + pdf、没有 md**：16 篇（如 `ssh连接`、`修复鲁班猫的监控例程`、`适用于rk3588的buildroot配置`）
- **只有 md**：20 篇（多数为较新的驱动/内核分析类）
- **只有 docx**：5 篇（`经验之谈`、`电源按一下开机`、`linux克隆github仓库问题`、`lubancat5 emmc备份`、`imx415预览偏绿`）

也就是说：**格式维度是 2~3 路分叉的，主题维度是 53 个单点**。用户来找资料时想的是"我摄像头预览偏绿怎么办"，而不是"我要 md 还是 pdf"。当前结构强迫用户先答一个他最不关心的选择题。

## 二、现有结构的五个问题

**P1 分区维度错位（最核心）**
`md源文档/` 与 `pdf文档/` 是按格式切分，导致同一主题被拆到两个目录。用户检索时必须"先进格式目录、再按文件名找"，且两个目录的文件名不完全对齐（`pdf文档/经验之谈.pdf` 这类并不存在，md 侧却有独有文档），无法靠目录做完整性校验。

**P2 同一主题散落三处**
例：`rv1106buildroot移植ffmpeg` 同时存在于 `学习文档/*.docx`、`pdf文档/*.pdf`；`linux开启swap` 在 `学习文档/` 有 md+pdf 两份而其他主题在 `md源文档/`。`学习文档/` 是拆分前的旧容器，从未清理，造成"同一篇资料有三条路径"。

**P3 根目录成为垃圾场**
`.deb` 内核包、124MB 的 `.7z`、例程压缩包、3 个 `*.txt` 便签、脚本与 README 同级。视觉上没有"这是资料库"的边界，新人 clone 后第一屏就是二进制包。

**P4 命名无统一规范，检索命中率低**
- 板卡称呼不统一：`猫1`、`鲁班猫5`、`lubancat5`、`6ull` 混用
- 无意义标题：`经验之谈`、`烧录问题`、`推送步骤`
- 版本号混入文件名：`ubuntu部署ai环境1.3.pdf`
- 全角标点、空格、`~$` 锁文件混在资料里

**P5 无索引、无元数据**
README 只有两句话 + 一张二维码。没有"文档目录表"，没有标注适用板卡/内核版本。同类问题（如三个输入法文档分属 20.04、debian11）只能靠文件名里的系统版本猜。

## 三、分类方案

### 3.1 设计原则

1. **主题优先，格式退位**：目录只表达"这是什么问题"，不表达"这是什么文件"。同主题的 md 与 pdf 同名并列同一目录。
2. **板卡型号不进目录**：型号写进元数据标签。理由见 4.1。
3. **一级 6 类 + 1 个收容所**：控制在 6±1，超过 7 个一级目录就等于没有分类。
4. **层级不超过 3 层**：`大类/子类/文件`。子类只在同类文档 ≥4 篇时才设。
5. **一稿一处，交叉靠链接**：跨域文档只放一处，另一处用相对链接指过去，不做副本。
6. **草稿与成品分离**：docx 草稿、脚本、固件包进带下划线前缀的私有目录（`_` 开头，默认不进 Git）。

## 四、分类依据与适用场景

### 4.1 为什么按"功能域"而不是"板卡型号"

数据上：53 篇文档里，**超过 60% 同时适用于多个型号**（如"安装 docker"对猫1~猫5 都成立，"永久旋转屏幕"猫2/猫3/猫4 通用）。若按型号建目录，同一篇要么复制多份（维护地狱），要么塞进某一个型号（其余型号找不到）。

而按功能域，每篇都有唯一归属，且和**排障时的思考顺序一致**：先想"是什么功能出问题"，再想"哪块板子"。型号作为标签存在 `board:` 字段里，检索"猫5 + PCIe"用 grep/front-matter 即可，比目录跳转更快。

**例外**：`6ull`、`RV1106` 属于不同产品线，资料量各只有 1~2 篇，不足以支撑一级目录，归入"发行版与异平台移植"并在标签里标 `board: 6ULL / RV1106`。

### 4.2 为什么格式不做目录，而是同名并列

- 用户下载时关心的是"这篇对不对"，格式是下载后才知道的细节；
- 同名并列后，`ls` 一眼就能看出"哪些文档还没有 pdf"（缺发布）或"哪些只有 pdf 没有 md"（缺源），形成天然的完整性检查；
- README 索引表里用一列"格式"标注 `md / pdf / md+pdf` 即可满足"我要 pdf"的诉求。

代价：不能再"整个 pdf 目录打包下载"。替代方案是 README 顶部给一条命令或一个 GitHub Release 附件，收益远大于损失。

### 4.3 为什么把"经验类"单独放 99

`经验之谈.docx` 这类文档没有单一功能域，强行塞进任一类都会污染该类。设 99 作为**显式收容所**，并配 `_inbox/` 作为未归类缓冲区——承认"分类总有漏网"，比追求 100% 归类更可持续。同时约定每月把 `_inbox` 清空，防止它变成第二个 `学习文档/`。

### 4.4 适用场景对照

| 使用者诉求 | 本方案给出的路径 |
|---|---|
| 现场排障：客户说"摄像头偏绿" | `03-驱动与设备树/01-摄像头/` 直接进，文件名即现象 |
| 新板卡上手：要装 Qt | `06-应用与AI/01-Qt开发环境/`，四篇按"装—配—错—补包"排好序 |
| 交付客户：要 PDF | README 索引表筛 `pdf` 列，或直接同目录取同名 pdf |
| 自己回顾：三个月前那个 U-Boot 改动 | `02-启动与内核/01-引导链/`，两篇按"实操—原理"分层 |
| 找固件包/脚本 | `_pkg/`、文档旁 `_assets/` |

## 六、命名规范

### 6.1 目录

```
NN-中文短名            # NN 两位数字：01~06 为功能域，99 为杂项，00 为规范
```
- 序号决定排序，新增一级目录时才重排；子目录同样带两位序号；
- 短名 2~6 字，不加"文档""资料""相关"；
- 下划线前缀（`_drafts`/`_pkg`/`_assets`/`_archive`）表示**工程性目录**，默认不进 Git 或单独处理。

### 6.2 文件

```
<对象>-<动作>[-限定].md
```
- **对象**：板卡/芯片/功能名，如 `imx415`、`鲁班猫5`、`Qt`、`VNC`
- **动作/结果**：从固定动词表里选，保证同类文档排序聚集

| 动词 | 含义 | 例 |
|---|---|---|
| 移植 | 把某驱动/系统搬到目标平台 | `ov8858驱动移植` |
| 配置 | 改配置项、写设备树/服务 | `rk3588-buildroot配置` |
| 安装 | 装软件、装库 | `板卡安装Qt5` |
| 修复 / 排查 | 已定位问题的解法 | `imx415预览偏绿修复` |
| 备份 / 还原 | 镜像与数据操作 | `dd整机备份与还原` |
| 实录 | 长过程记录（多步骤项目） | `鲁班猫-Lakka移植实录` |

- **限定**：仅在需要消歧时加，如 `板卡安装Qt5` vs `Qt交叉编译环境配置`

### 6.3 硬性禁止项

- ❌ 空格、全角标点 `（）`、`+`、`：`、`，`（用 `-` 替代）
- ❌ `~$` 前缀文件（Word 锁文件，入 `.gitignore` 并定期清理）
- ❌ 版本号入文件名（版本写进 front-matter 的 `version`，文件名只留主版本语义）
- ❌ 口语化/无信息标题（`经验之谈`、`问题`、`方案`、`推送步骤`）
- ❌ `猫1` 与 `鲁班猫1` 混用：文件名统一写 `鲁班猫1`，正文可简称"猫1"

### 6.4 多格式与附件

- 同一主题多格式 → **同名并列**：`xxx.md` + `xxx.pdf`，不建 `pdf/`、`md/` 分目录
- 配图与专属附件 → `_assets/<文档名>/`，图片按 `01-描述.png` 编号
- 通用大文件（deb/7z/固件）→ `_pkg/`，Git 侧用 LFS 或改挂 Release
- 图片引用一律**相对路径**：`![alt](_assets/xxx/01-err.png)`，避免 `../../../` 跨层跳转

### 6.5 文档头部元数据（front-matter）

```yaml
---
title: imx415 4K60fps 驱动移植
summary: 改设备树与驱动支持 4K60fps，含 Kconfig/Makefile 改动与 iqfile 命名规则
board: [鲁班猫4]          # 多板卡用数组；跨平台写 all
soc: RK3588S
kernel: 5.10.160
os: Ubuntu 20.04
tags: [摄像头, 设备树, sensor]
updated: 2026-07-31
formats: [md, pdf]
---
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `title` | 是 | 中文标题，可与文件名一致 |
| `summary` | 是 | 一句话说明，直接进 README 索引表的「说明」列 |
| `board` | 是 | 板卡数组；通用写 `[鲁班猫]` |
| `soc` / `kernel` / `os` / `arch` | 视情况 | 文档明确时才写；`kernel: "6.1"` 必须加引号，否则 YAML 解析成浮点数 |
| `tags` | 是 | 2~4 个，功能域 + 技术点 |
| `updated` | 是 | 最后**内容**修改日期（补元数据不算） |
| `formats` | 是 | `[md]` 或 `[md, pdf]` |

作用：① `gen-index.ps1` 据此自动生成 README 索引表，新增文档不必手改 README；② 型号/内核不再需要进目录名；③ 后续接入静态站点或全文检索时有结构化字段。

## 七、层级深度与拆分 / 合并规则

**层级：固定 3 层，不设第 4 层。**
`大类 / 子类 / 文件`。若出现"文件里还要再分目录"的冲动，说明该子类该升级为一级目录，或该主题该拆成多篇。

**子类设立阈值：同类文档 ≥4 篇。**
- 3 篇及以下 → 直接平铺在大类下，不建空壳子目录
- 例：`03-驱动与设备树/04-串口与总线` 目前只有 2 篇，若后续无新增，可合并回大类平铺

**拆分阈值：单篇超过 300 行或含 3 个以上独立故障现象 → 拆。**
- 拆分方式：`xxx-part1-现象.md` / `xxx-part2-解法.md`，同目录并列，part1 末尾链 part2
- 反例警告：`Lakka移植实录` 68KB 属超长文档，但它是一条线性流程（按章节读），**不拆**——判断标准是"读者是否需要跳读"，而非单纯字数

**合并规则：同一主题的 md/pdf/docx 一律合并为一份源（md）+ 一份成品（pdf）。**
docx 若为唯一源（当前 5 篇），先转 md 入库，docx 留在同一目录作备份。

**大类数量上限：7 个（含 99）。**
超过说明分类粒度过细；低于 4 个说明过粗，都会降低检索效率。

```

  │
  ├─ Q4 该大类下有无现成子类？（看子类名能否覆盖）
  │     ├─ 有 → 放入
```

## 十、风险与待确认

1. **外部链接失效**：若 PDF 被外部（客户、群聊）以直链方式引用，迁移后 404。缓解：`MIGRATION.md` 保留对照表，GitHub 侧旧路径文件暂留一个 tag 版本。
2. **`.git` 体积**：历史中的 124MB 7z 无法通过移动删除，只能止血。是否接受 `filter-repo` 改写历史，需要你决定。
3. **`经验之谈.docx`（1MB）**：内容是散记还是已成体系？若内容较杂，建议按第八章决策流程拆分后分发，而不是整体放 99。
4. **`99` 是否必要**：若你倾向"全部内容都必须有归属"，可取消 99，用 `_inbox` + 月度强制归档替代；但历史经验表明收容所更实用。
5. **是否引入静态站点**（如 VitePress/mkdocs）：front-matter 已为此预留；若要公网可读，这是下一步。
